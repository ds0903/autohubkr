# АвтоХаб КР: ШІ-навігатор автопослуг (Кривий Ріг)

Платформа, де клієнт описує проблему з авто, отримує припущення від ШІ, залишає заявку виконавцю й веде гараж.
Реалізація за ТЗ «Концепція v2.0». Ядро: **каталог → заявка → підтверджена угода**.

## Стек
Python 3.13 · Django 5.2 · PostgreSQL 17 · Gemini (`google-genai`) · aiogram 3 · HTMX

## Швидкий старт
```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env            # впишіть DB_PASSWORD, GEMINI_API_KEY, TELEGRAM_BOT_TOKEN
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py seed_initial       # місто, категорії, типи послуг, марки, нормативи ТО
.\.venv\Scripts\python.exe manage.py createsuperuser    # роль «Адміністратор» виставте в адмінці
.\.venv\Scripts\python.exe manage.py runserver          # сайт: http://127.0.0.1:8000  адмінка: /admin/
.\.venv\Scripts\python.exe manage.py runbot             # Telegram-бот (потрібен токен)
# Профіль на сайті показує кнопку «Підключити в Telegram» (t.me/<бот>?start=link-код) лише коли бот є:
# задано TELEGRAM_BOT_TOKEN (ім'я бота визначається само) або TELEGRAM_BOT_USERNAME. Без бота блоку немає.
.\.venv\Scripts\python.exe manage.py test               # юніт, інтеграційні та E2E тести
```
Перевірка ШІ перед запуском: `manage.py check_ai` робить один справжній запит до Gemini і показує модель.
Без цього збій (знята модель, квота, неправильний ключ) непомітний: сайт мовчки переходить на підбір за ключовими
словами. Збої також пишуться в лог і в `Message.meta["llm_failed"]`. Модель задає `GEMINI_MODEL`
(`gemini-2.5-flash` для нових ключів уже недоступна), очікування відповіді обмежує `GEMINI_TIMEOUT_SECONDS`.

Демо-виконавці для розробки: `manage.py seed_demo` (видалити: `seed_demo --clear`). Усі демо-записи позначені «ДЕМО-ДАНІ».

### Наповнення бази виконавцями
* Масовий імпорт із CSV: `manage.py import_providers файл.csv --city kr [--delimiter ";"] [--dry-run]`.
  Колонки: `name, categories, district, address, phone, telegram, website, working_hours, brands, source`
  (категорії й марки через `;`). Імпорт ідемпотентний: повторний запуск оновлює, порожні значення наявних не затирають.
* Підтвердження даних власником (розділ 9 ТЗ) і особиста ссилка/QR для його клієнтів (розділ 7.2): в адмінці
  «Виконавці» → дія «Показати посилання». Лінки: `/confirm/<токен>/` (діє 30 днів), `/r/<код>/` і `/r/<код>/qr.svg`.
  Клієнти, що прийшли за особистою ссилкою, позначаються `lead_origin = provider_own` (без комісії в майбутньому).
* SEO: `/sitemap.xml`, `/robots.txt`.

### Локальна база
У `.env` стоїть окремий dev-кластер PostgreSQL у `.pgdata/` (порт **5433**), створений, щоб не чіпати ваш основний
інстанс. Кластер створено без ICU (`--locale-provider=builtin`) і з `jit = off`.

**Відома проблема розробницького середовища.** На машині розробки процеси `postgres.exe` періодично падали з
`0xC0000005` («Faulting module: unknown», завжди однаковий зсув `…44d0`), навіть з вимкненими ICU та JIT; причину не
встановлено. Падіння відбувалися в різних місцях прогону (звичайні тести й E2E), тому повний набір на цій машині
стабільно на Postgres не проходив. Для перевірки логіки є запасний режим:
```powershell
$env:DB_ENGINE="sqlite"; .\.venv\Scripts\python.exe manage.py test
```
Бойове середовище й розробка мають працювати на PostgreSQL. Повний набір тестів слід прогнати на стабільному Postgres
(інша машина, CI або Docker) до запуску в роботу.
Після перезавантаження ПК запустіть кластер:
```powershell
& "C:\Program Files\PostgreSQL\17\bin\pg_ctl.exe" start -D .pgdata -o "-p 5433" -l .pgdata.log
```
Щоб використовувати свій Postgres, змініть `DB_HOST/DB_PORT/DB_USER/DB_PASSWORD` у `.env` і створіть базу `autohubkr`.

## Розгортання на сервері (Ubuntu, без Docker)
Файли в `deploy/`: два systemd-сервіси (`autohubkr-web` на gunicorn 127.0.0.1:8390 і `autohubkr-bot`), блок nginx,
шаблон `.env` і скрипт `deploy.sh`. Скрипт ідемпотентний і працює на спільному сервері: не оновлює системні пакети,
не чіпає firewall та чужі сайти, створює лише власну роль і базу Postgres, власні unit-файли й server-блок nginx.

```bash
# код лежить у /srv/autohubkr/app (git clone, git pull або розпакований архів)
cd /srv/autohubkr/app && SERVER_NAME=<IP або домен> bash deploy/deploy.sh
```
- Якщо `.env` ще немає, скрипт створює його зі згенерованими `DJANGO_SECRET_KEY` і паролем БД; існуючий `.env` не змінює.
  `GEMINI_API_KEY` і `TELEGRAM_BOT_TOKEN` вписує власник сам, потім `sudo systemctl enable --now autohubkr-bot` і
  `sudo systemctl restart autohubkr-web`. Без токена бот не запускається.
- З `DJANGO_DEBUG=0` проєкт не стартує зі слабким `DJANGO_SECRET_KEY`. Статика отримує хеші в іменах (`collectstatic`),
  кеш лежить у БД (`CACHE_BACKEND=db`), щоб його ділили воркери gunicorn.
- Назовні віддаються лише фото виконавців (`/media/providers/`); фото заявок і чеки містять персональні дані й закриті.
- Домен і https: додайте домен у `SERVER_NAME`, випустіть сертифікат (`certbot --nginx`), у `.env` поставте `DJANGO_HTTPS=1`
  (Secure-cookie, заголовок проксі) і `DJANGO_CSRF_TRUSTED_ORIGINS=https://домен`, потім перезапустіть `autohubkr-web`.
- Суперкористувач: `cd /srv/autohubkr/app && ../venv/bin/python manage.py createsuperuser`, роль задається в адмінці.

## Ключові рішення
* **Угода** = «роботу виконано і підтверджено обома сторонами» (`Order.is_confirmed_deal`). Тільки вона дає запис
  «підтверджено виконавцем» у гаражі, лічильник виконавця й право на відгук.
* Усі переходи статусів проходять через `apps/orders/services.py` → журнал із відповідальним і часом.
* **Контакти виконавця** приховані, поки заявка не в статусі «Запис» (`Order.contacts_visible`).
* **ШІ** не називає цін і виконавців сам: тип послуги обирає модель із довідника, виконавців підбирає код за
  пояснюваними правилами, ціни беруться лише з прайсу в базі, платне просування позначається «реклама».
  Безпекові теми (гальма, кермо, колеса, подушки) завжди дають попередження: це перевіряється кодом незалежно від моделі.
* Діалоги з ШІ зберігаються **лише за згодою** користувача; без згоди записуються тільки службові мітки.
* Робота зв'язкового: адмінка → «Заявки» (дії для переходів, пропозиції, журнал обходу) та звіт з метриками пілота
  (`/admin/orders/order/report/`).
* Telegram-сповіщення йдуть через таблицю `Notification`: сервіси лише ставлять у чергу, бот надсилає й повторює спроби.

## Ролі
| Роль | Як працює |
|---|---|
| Клієнт | сайт і бот |
| Виконавець | бот: кнопки «Беру / Відмовитись», `/visit`, `/estimate`, `/done`. Акаунт з роллю «Виконавець», `telegram_id` і прив'язкою до картки (`owner`) створює зв'язковий в адмінці. Свій Telegram ID виконавець бачить командою `/myid` |
| Зв'язковий | адмінка; отримує сповіщення про нові заявки та відмови, якщо вказано його `telegram_id` |
| Адміністратор | адмінка: база, модерація відгуків і фото |

## Що ще потрібно від людей (не код)
Юридичні тексти (оферти, політика, формулювання гарантії), реальна база 100–150 виконавців, вилки цін від перших 15–20,
джерело VIN-декодування для європейських авто, нормативи ТО для популярних моделей.
